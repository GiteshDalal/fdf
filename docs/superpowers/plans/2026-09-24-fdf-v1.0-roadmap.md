# FDF 1.0 — delivery roadmap

**Spec:** [2026-09-24-fdf-v1.0-design.md](../specs/2026-09-24-fdf-v1.0-design.md)

The 1.0 design spans five subsystems that depend on each other in order: the
foundations, the validator, the commands, `fdf migrate`, and the install,
skills and documentation. It is delivered as five plans, each written in full
once the one before it has landed, because each plan builds on the exact APIs
its predecessor creates.

The plans **expand, then contract**. Plans 1 to 4 add 1.0 beside 0.x, so every
step leaves the tests green; Plan 5 removes 0.x and ships. No release is cut
from the integration branch until Plan 5 is done.

## Branches

- **`v1`** is the integration branch, created from `claude/v1-0-design` (which
  holds the design, this roadmap and the plans) once they are reviewed.
- **Each plan** is worked on a branch off `v1` and merged into `v1` by pull
  request, once CI passes (`go vet ./...`, `go test ./...`, `gofmt -l .`
  printing nothing, and the skills' frontmatter lint).
- **0.7.1** fixes `fdf mv` for everyone still on 0.7, and is released from
  `main`. Plan 1 is done, so 0.7.1 is five of its commits cherry-picked onto a
  branch off `main`: ff7e809 (the `links` engine), 40635f6 (`fdf mv` on it),
  51abc22 (`fdf log` reads the pin as the validator does), 20bce8f
  (angle-bracket destinations) and 1546a13 (a listing found by its first
  link). None needs `specver`. Only CLAUDE.md conflicts, on ff7e809: put the
  `links` bullet after the `fdfroot` bullet. They fix these defects in 0.7.0:
  - links that leave the bundle break on a move that changes depth;
  - a footnote's first word is rewritten as a path;
  - a reference definition inside a code fence is rewritten;
  - on a moved index listing line, URLs, anchors and mail links are rewritten
    as paths;
  - a destination written as `<path>` loses its opening bracket to the path;
  - a listing line that links on to other documents stays behind when its
    document changes group, and another document's listing that mentions the
    moved one is carried off in its place;
  - `fdf log` refuses a draft's log under a single-quoted pin that
    `fdf validate` accepts.

  When 0.7.1 lands, merge `main` into `v1`. Only CLAUDE.md conflicts: keep
  `v1`'s side.
- **When Plan 5 is done**, `v1` merges into `main` and `v1.0.0` is tagged
  there.

## Carried forward from Plan 1

Plan 1's reviews left these for the plans that own them.

Plan 2 did its items: `links.Find` reads every listed form, `links.Resolve` is
exported and shared, `bundle.pinAtLeast` takes a `specver.Version`, and every
`supportedVersions` key is tested to parse.

Plan 3 did its items: the commands' one gate, `scaffold.RequireSupported`,
reads the pin as a `specver.Version`, and no 0.x minor is left in `scaffold`;
`migrate` names its own target, 0.7, and refuses a 1.0 pin before the pre-0.4
chain can run; and `scaffold.ListingTarget` reads a listing's first link with
`links.Find`, so one whose link has a title or a `<…>` destination is found.

Plan 4 did its item: a link from the bundle root whose target leaves the new
base stays relative once `links.Retarget` rewrites it, as spec 1.0's
*Cross-linking* writes a link to a file outside the bundle, and a test holds
it there, beside one showing such a link unchanged while the base stays put.

## Carried forward from Plan 2

Plan 3 did its items: every command writes 1.0 through `layout`; `ReservedDirs`
and its test went with the 0.x layout, and `TestNewRefusesWhatTheValidatorRejects`
holds `fdf new` to the validator; the moves `fdf lexicon` suggests are ones
`fdf mv` makes; the conformance harness finds a `repo/` fixture's bundle as fdf
does, and `resource-missing-v10` tests R1; `fdf migrate` refuses a pin at or
above 1.0; and `spec/1.0.md` settles that a directory that holds no Markdown,
at any depth, is outside FDF in a register as at the root. F3 already read it
so, F12 (`groupName`) now does, and such a directory, misnamed or not, is never
reported.

Plan 4 did its items: `links.Find` reads all five of the gaps Plan 2 found
as CommonMark does — (a) a fence marker indented four columns opens no fence,
(b) a heading ends its block, (c) a destination's balanced parentheses and
escapes are part of it, (d) a reference definition that would interrupt a
paragraph, an escaped bracket and one in a code span are text, and (e) a line
indented four columns after a heading or a closing fence is code — and every
fixture's `fdf validate` output is as it was.

**Plan 5 (contract and ship):**
- A pin the validator does not support is still validated under v0.2's rules
  after its F1 error. With 0.x gone, validation stops at F1.
- A bundle with no pin is still validated under v0.2's rules, with a
  warning. With 0.x gone, a missing pin is an F1 error, and the "validated
  under v0.2 rules" warning goes (design §4).
- The 0.x code to remove: `visitV0` in `validate.go`; the `stem`, `v5`, `v6`
  and `v7` gates in `collection` and in the checks; `linkRe` and the 0.x
  branches of `resolveLink` and `sectionLinks`; `dirName`, `registerDirs` and
  `checkDomain`.
- The 1.0 fixtures carry a `-v10` suffix, which goes with every other `-vNN`.
- `spec/README.md` and `SPEC.md` do not list `spec/1.0.md` yet.
- F6 and F7 place a reference-style link by where its definition sits
  (`sectionTargets`): `[01-signup-form.md][signup]` in `# Tasks`, with the
  definition at the end of the plan, gives a false F6, and a lone definition
  inside the section, which renders nothing, counts as a listing. 0.x
  ignored reference links entirely, so this is not a regression.
- An orphan task at a register root gets a misleading message
  (`documentV1` in `walk.go`): `features/01-api.md`, typed Task, is told
  that `features.md` does not exist, a file the closed root forbids.
- A group named like a flat feature, `features/onboarding/` beside
  `features/onboarding.md`, is that feature's task directory, so the
  documents filed in it are reported only as "task directories may contain
  only NN-slug.md tasks". The message could name the clashing
  `features/onboarding.md`.

## Carried forward from Plan 3

Plan 4 did its items: `fdf migrate` takes any 0.x bundle to 1.0 (`target`),
and a bundle already at 1.0 takes design §6's repair path. It keeps its
refusal of a root inside a pinned bundle, refuses a document named
`index.md` or `log.md`, and moves a v0.6 `bugs/` feature group to
`features/bugs/`, so `bugsGroupConflict` went. Migrate plans its indexes as
text (`scaffold.IndexText`, `ContextStub`, `SpecDoc`, `RegisterLine`,
`WithRegisterListing`), so the writers only it used, `EnsureChangesIndex`
and its three siblings, `RefreshSpec` and `EnsureContextStubs`, went; the
migrated root index lists the registers as `fdf init`'s does. It also
folded in the item Plan 3's final review parked: `fdf init` refuses a root
inside a pinned bundle, in `fdfroot.InsideBundle`'s words.

**Plan 5 (contract and ship):**
- `fdf install` still names `docs/features` in the skills when no root is
  given, and the skills and primer describe 0.7, while `fdf init` now
  creates `docs/fdf/`.
- The validator still checks 0.x pins that the commands refuse. The tests
  that show a command refusing a 0.x bundle copy `valid-bugs-v07`, or pin
  0.x inline; they need a 0.x bundle only for that refusal once the 0.x
  fixtures go.
- `main.version` still reads 0.7.0.
- No test now fails when a spec version is embedded without its Context
  documents being known: that tripwire was `TestReservedDirsMirrorTheValidator`,
  which went with `ReservedDirs`. The version-bump steps in `CLAUDE.md` are
  what remains.
- One pin reader. Four read a pin: the validator's `readPin` parses the
  frontmatter; `scaffold.Pin` finds the root `INDEX.md`'s `fdf_version` line
  by line; `fdfroot.pinned`, which `BundleAbove` asks too, matches an
  `fdf_version:` line anywhere in an `INDEX.md`, one in a fenced sample in
  its body included; and migrate's `readPin` matches one anywhere in the
  file. When another line of the frontmatter does not parse, the commands
  see the pin and the validator sees none, and checks the bundle under
  0.2's rules. Once the validator drops 0.x, share one reader among all
  four, and report frontmatter that does not parse as F1. Until migrate
  stops treating a missing pin as 0.x, its guard must keep a reader as
  lenient as `scaffold.Pin`, or it would run the 0.x steps on such a 1.0
  bundle.
- F1 still sends a pin that does not parse, such as `1.0.0` or `v1.0`, to
  `fdf migrate`. The commands' gate and migrate now say it is not a
  `MAJOR.MINOR` version, to be corrected in `INDEX.md`; F1 should say the
  same, and not point at `fdf migrate`.
- The release notes say where fdf looks: `docs/features` counts only when
  its `INDEX.md` pins `fdf_version`. A bundle there with no `INDEX.md`, or
  one with no pin, which 0.7's fdf validated by default under 0.2's rules,
  now needs `--root`.
- `fdf mv features/core features/index` is refused, although a group named
  `index` or `log` is legal (`Place` allows `features/index/overview`): `mv`
  checks a group's destination with `Place`, whose slug check is meant for a
  document, and on a disk that ignores case the refusal comes earlier
  still, as a misleading "already exists" (`index.md` matches `INDEX.md`).
  Nothing is written. The fix is in how `mv` checks a group's destination
  on such a disk.
- `fdf init` on an existing bundle restores a missing `SPEC.md` for the
  current version (`EnsureSpec`), not for the version the bundle pins. It
  is latent while 1.0 is the only 1.x; before any 1.1, init restores the
  spec its pin names.
- `fdf log` reads the bundle to parse its arguments before the gate:
  `runLog` asks `logs.IsID` whether a lone argument names a document before
  `logs.Append` asks `RequireSupported`. It only reads, but the gate is to
  come before a command reads anything.

## Carried forward from Plan 4

**Plan 5 (contract and ship):**
- Migrate's next step sends the user to `fdf install`, which still writes the
  0.7 skills and a primer naming `docs/features` (Plan 3's item above).
- The 0.x fixtures that validate today, migrated in a scratch run, came out
  conformant but for what 0.7's own rules add (F8's `## <scenario name>`
  cases, a `timestamp`'s form, a declaration line that wraps) and one stray
  root file, which migrate refuses: `root-log-type-v03`'s `worklog.md`. Plan
  5's conversion fixes those by hand after migrating.
- `fdf mv` rewrites a feature ID where it begins a `resource` or
  `applies-to` path (`refactor.IDMentions` skips only link targets), which
  migrate skips (`fieldPaths`). `mv` should skip them too.
- Outside a git repository, migrate rewrites no mention of the bundle's path
  inside the bundle either: without a project root it cannot tell the
  bundle's path.
- A monorepo component's own mention of its bundle, `docs/features` in
  `services/api/README.md` for a bundle at `services/api/docs/features`, is
  not the bundle's path from the project root, so migrate neither rewrites
  it nor lists it. Nor does it reach the superproject of a bundle below a
  submodule's root (a submodule `docs/` holding `features/`): the
  submodule's repository tracks the bundle, and migrate works in it.
- A group with no index, which the root never listed, gets a listing of its
  directory in `features/INDEX.md`, and no index of its own. A `releases/`
  with no `INDEX.md` gets none either, and the root lists it only once
  `fdf release` writes one.
- A group the root lists in an ordered list or a table is no listing, as
  listings are bullets: its line stays in the root `INDEX.md`, its link
  repaired, and `features/INDEX.md` gets a generated listing without its
  description.
- Inside the bundle, a mention of a group's path that is no feature ID, such
  as `venues/INDEX.md` in prose, is not rewritten: only IDs, links and the
  bundle's path are.
- An unpinned bundle already in the stem layout is refused by the 0.1–0.3
  pre-flight, which reads every `slug.spec.md` as a dotted name; the message
  could say to add the pin the bundle was written for (as before Plan 4).
- A destination's parent directories that `--to` created stay behind, empty,
  after the undo commands of a migration that stopped partway, and after the
  commands that back out one that went through. So does a hidden file git
  ignores, such as a Finder `.DS_Store`, in a group that had moved: it
  stays at `features/<group>/`, and the next run refuses the group's place
  as taken until it is removed.
- Migrate exits with the validator's code (design Decision 19), so a bundle
  that migrates but fails 0.7's rules exits 1 after `done` (ginee: 299 F8
  and F10 errors). Plan 5's conversion meets it.
- The clean-tree check and the printed undo put every outside file migrate
  rewrites on one command line, which a very large monorepo could push past
  the system's argument-length limit. The check then fails safely, before
  anything is written; `--pathspec-from-file` would scale.
- The check for a place git would ignore reads each `.gitignore` where it is
  before anything moves, so the rules of one inside the bundle are not read
  where the bundle takes them: a file git tracks that such a rule ignores
  (`*.png` in `docs/features/.gitignore`, with a diagram force-added) still
  drops out of git once it moves. Reading those rules at their new place
  means matching ignore patterns without git, or checking again once moved.
- `fdf migrate --skip <glob>` (design Decision 17): migrate leaves the files
  it names as they are, such as applied SQL migrations whose checksums a
  tool verifies, and lists their mentions of the old path.
- An absolute symbolic link into the bundle, which the move breaks, is
  listed with what migrate leaves behind (design Decision 20); today it goes
  unmentioned.
- A register's place taken by a plain file, a `practices` file at the root,
  stops migrate partway, with correct undo commands; it should be refused
  before anything is written, as a `features` file is.
- `stripStatusTags` keeps its own fence test, which a prose line that opens
  a backtick run and closes it on the same line takes for a fence: the case
  `links.Find` no longer misreads. It should read fences as `links` does.
- The test of the printed back-out commands covers a plain directory and a
  submodule, not a bundle that is its own repository.
- Plan 4 decided what design §6 left open, and on 2026-09-26 the design's
  owner approved each: the design records them (*Decisions* 13 to 21, and
  §6's text). Where the approved design asks for more than Plan 4 built
  (`--skip`, the listing of an absolute symbolic link, the refusal of a
  register's place taken by a file), the items above carry it.
- Migrate's minor-version path (1.0 to 1.x: move the pin, re-vendor
  `SPEC.md`, create any new register's `INDEX.md`, edit no document, design
  §4) waits for 1.1; today it repairs a bundle at `target` only.
