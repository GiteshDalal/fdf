# FDF 1.0 — delivery roadmap

**Spec:** [2026-09-24-fdf-v1.0-design.md](../specs/2026-09-24-fdf-v1.0-design.md)

The 1.0 design spans five subsystems that depend on each other in order: the
foundations, the validator, the commands, `fdf migrate`, and the install,
skills and documentation. It is delivered as five plans, each written in full
once the one before it has landed, because each plan builds on the exact APIs
its predecessor creates.

The plans **expand, then contract**. Plans 1 to 4 add 1.0 beside 0.x, so every
step leaves the tests green; Plan 5 removes 0.x and ships. No release is cut
from the integration branch until Plan 5 is done.

## Branches

- **`v1`** is the integration branch, created from `claude/v1-0-design` (which
  holds the design, this roadmap and the plans) once they are reviewed.
- **Each plan** is worked on a branch off `v1` and merged into `v1` by pull
  request, once CI passes (`go vet ./...`, `go test ./...`, `gofmt -l .`
  printing nothing, and the skills' frontmatter lint).
- **0.7.1** fixes `fdf mv` for everyone still on 0.7, and is released from
  `main`. Plan 1 is done, so 0.7.1 is five of its commits cherry-picked onto a
  branch off `main`: ff7e809 (the `links` engine), 40635f6 (`fdf mv` on it),
  51abc22 (`fdf log` reads the pin as the validator does), 20bce8f
  (angle-bracket destinations) and 1546a13 (a listing found by its first
  link). None needs `specver`. Only CLAUDE.md conflicts, on ff7e809: put the
  `links` bullet after the `fdfroot` bullet. They fix these defects in 0.7.0:
  - links that leave the bundle break on a move that changes depth;
  - a footnote's first word is rewritten as a path;
  - a reference definition inside a code fence is rewritten;
  - on a moved index listing line, URLs, anchors and mail links are rewritten
    as paths;
  - a destination written as `<path>` loses its opening bracket to the path;
  - a listing line that links on to other documents stays behind when its
    document changes group, and another document's listing that mentions the
    moved one is carried off in its place;
  - `fdf log` refuses a draft's log under a single-quoted pin that
    `fdf validate` accepts.

  When 0.7.1 lands, merge `main` into `v1`. Only CLAUDE.md conflicts: keep
  `v1`'s side.
- **When Plan 5 is done**, `v1` merges into `main` and `v1.0.0` is tagged
  there.

## Carried forward from Plan 2

Plan 3 did its items: every command writes 1.0 through `layout`; `ReservedDirs`
and its test went with the 0.x layout, and `TestNewRefusesWhatTheValidatorRejects`
holds `fdf new` to the validator; the moves `fdf lexicon` suggests are ones
`fdf mv` makes; the conformance harness finds a `repo/` fixture's bundle as fdf
does, and `resource-missing-v10` tests R1; `fdf migrate` refuses a pin at or
above 1.0; and `spec/1.0.md` settles that a directory that holds no Markdown,
at any depth, is outside FDF in a register as at the root. F3 already read it
so, F12 (`groupName`) now does, and such a directory, misnamed or not, is never
reported.

**Plan 4 (`fdf migrate`):**
- `links.Find` has five known gaps. (a) and (c) must be fixed before
  `fdf migrate` runs the engine over a whole project, where every tracked
  text file passes through it.
  - (a) A fence marker indented four spaces or more still opens a fence,
    where CommonMark reads the line as indented code, because `Find` tests
    for a fence before it tests for indented code; if nothing closes it, the
    rest of the text counts as code.
  - (b) A heading does not end its block for code-span pairing, so a stray
    backtick in a heading can hide a link on the next line.
  - (c) Balanced parentheses in a destination are misread:
    `[a](five(1).md)` gives the target `five(1`.
  - (d) A reference definition that interrupts a paragraph, an escaped `\[`,
    and a `[` inside a code span are each read as a link.
  - (e) A line indented four columns right after a closing fence or a
    heading is read as prose, where CommonMark reads an indented code block,
    because `Find` wants a blank line before indented code. F6 and F7 now
    follow `Find` there, as the broken-link check does.

**Plan 5 (contract and ship):**
- A pin the validator does not support is still validated under v0.2's rules
  after its F1 error. With 0.x gone, validation stops at F1.
- A bundle with no pin is still validated under v0.2's rules, with a
  warning. With 0.x gone, a missing pin is an F1 error, and the "validated
  under v0.2 rules" warning goes (design §4).
- The 0.x code to remove: `visitV0` in `validate.go`; the `stem`, `v5`, `v6`
  and `v7` gates in `collection` and in the checks; `linkRe` and the 0.x
  branches of `resolveLink` and `sectionLinks`; `dirName`, `registerDirs` and
  `checkDomain`.
- The 1.0 fixtures carry a `-v10` suffix, which goes with every other `-vNN`.
- `spec/README.md` and `SPEC.md` do not list `spec/1.0.md` yet.
- F6 and F7 place a reference-style link by where its definition sits
  (`sectionTargets`): `[01-signup-form.md][signup]` in `# Tasks`, with the
  definition at the end of the plan, gives a false F6, and a lone definition
  inside the section, which renders nothing, counts as a listing. 0.x
  ignored reference links entirely, so this is not a regression.
- An orphan task at a register root gets a misleading message
  (`documentV1` in `walk.go`): `features/01-api.md`, typed Task, is told
  that `features.md` does not exist, a file the closed root forbids.
- A group named like a flat feature, `features/onboarding/` beside
  `features/onboarding.md`, is that feature's task directory, so the
  documents filed in it are reported only as "task directories may contain
  only NN-slug.md tasks". The message could name the clashing
  `features/onboarding.md`.

## Carried forward from Plan 3

**Plan 4 (`fdf migrate`):**
- `migrate` upgrades a 0.x bundle to 0.7 (`target` in `migrate.go`) and
  refuses a pin at or above 1.0. Replace both: the step to 1.0, and design
  §6's repair path for a bundle already at 1.0.
- Until then a 0.x bundle has no way to 1.0. Every command but `validate`,
  `migrate` and `serve`, `fdf init` included, sends it to `fdf migrate`,
  which stops at 0.7 and then says there is nothing to migrate.
- `fdf migrate` refuses a root inside a pinned bundle: one whose own
  `INDEX.md` pins nothing, below a directory whose `INDEX.md` pins a version
  (`fdfroot.BundleAbove`), such as `--root docs/fdf/features`, where its
  steps built a second bundle inside the register. It changes nothing, and
  says what the commands' gate says (`fdfroot.InsideBundle`). The migrate
  that replaces it keeps this refusal.
- `spec/1.0.md` now has migrate refuse a document named `index.md` or
  `log.md`, which 1.0 makes an F3 error: a disk that ignores case reads one
  as the `INDEX.md` or `LOG.md` beside it.
- `fdf mv` refuses a 0.x bundle, so migrate's refusal of a v0.6 `bugs/`
  feature group (`bugsGroupConflict`) now asks for the group to be renamed by
  hand, and `TestMigrateAfterMovingTheBugsFeatureGroup` renames it by hand.
  Design §6 moves such a group to `features/bugs/`, and the refusal goes.
- `scaffold.EnsureChangesIndex`, `EnsurePracticesIndex`, `EnsureDebtsIndex`
  and `EnsureBugsIndex` remain only for migrate; `EnsureIndex` writes any
  register's, `features` included. `RefreshSpec` takes the version it
  vendors.
- `fdf init`'s root `INDEX.md` lists the registers with
  `scaffold.registerListings`, and `ListRegister` adds one after them. The
  migrated root index should list them the same way.

**Plan 5 (contract and ship):**
- `fdf install` still names `docs/features` in the skills when no root is
  given, and the skills and primer describe 0.7, while `fdf init` now
  creates `docs/fdf/`.
- The validator still checks 0.x pins that the commands refuse. The tests
  that show a command refusing a 0.x bundle copy `valid-bugs-v07`, or pin
  0.x inline; they need a 0.x bundle only for that refusal once the 0.x
  fixtures go.
- `main.version` still reads 0.7.0.
- No test now fails when a spec version is embedded without its Context
  documents being known: that tripwire was `TestReservedDirsMirrorTheValidator`,
  which went with `ReservedDirs`. The version-bump steps in `CLAUDE.md` are
  what remains.
- One pin reader. Four read a pin: the validator's `readPin` parses the
  frontmatter; `scaffold.Pin` finds the root `INDEX.md`'s `fdf_version` line
  by line; `fdfroot.pinned`, which `BundleAbove` asks too, matches an
  `fdf_version:` line anywhere in an `INDEX.md`, one in a fenced sample in
  its body included; and migrate's `readPin` matches one anywhere in the
  file. When another line of the frontmatter does not parse, the commands
  see the pin and the validator sees none, and checks the bundle under
  0.2's rules. Once the validator drops 0.x, share one reader among all
  four, and report frontmatter that does not parse as F1. Until migrate
  stops treating a missing pin as 0.x, its guard must keep a reader as
  lenient as `scaffold.Pin`, or it would run the 0.x steps on such a 1.0
  bundle.
- F1 still sends a pin that does not parse, such as `1.0.0` or `v1.0`, to
  `fdf migrate`. The commands' gate and migrate now say it is not a
  `MAJOR.MINOR` version, to be corrected in `INDEX.md`; F1 should say the
  same, and not point at `fdf migrate`.
- The release notes say where fdf looks: `docs/features` counts only when
  its `INDEX.md` pins `fdf_version`. A bundle there with no `INDEX.md`, or
  one with no pin, which 0.7's fdf validated by default under 0.2's rules,
  now needs `--root`.
- `fdf mv features/core features/index` is refused, although a group named
  `index` or `log` is legal (`Place` allows `features/index/overview`): `mv`
  checks a group's destination with `Place`, whose slug check is meant for a
  document, and on a disk that ignores case the refusal comes earlier
  still, as a misleading "already exists" (`index.md` matches `INDEX.md`).
  Nothing is written. The fix is in how `mv` checks a group's destination
  on such a disk.
- `fdf init` on an existing bundle restores a missing `SPEC.md` for the
  current version (`EnsureSpec`), not for the version the bundle pins. It
  is latent while 1.0 is the only 1.x; before any 1.1, init restores the
  spec its pin names.
- `fdf log` reads the bundle to parse its arguments before the gate:
  `runLog` asks `logs.IsID` whether a lone argument names a document before
  `logs.Append` asks `RequireSupported`. It only reads, but the gate is to
  come before a command reads anything.
