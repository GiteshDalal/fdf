# FDF 1.0 — the bundle reorganised

**Date:** 2026-09-24
**Status:** approved in conversation on 2026-09-24, section by section; this
written spec awaits review.

## Summary

FDF began as a bundle of features. The registers arrived one version at a
time, `changes/` in 0.5, `practices/` and `debts/` in 0.6 and `bugs/` in 0.7,
and each took its name from the feature groups that share the bundle root. On
a large project the root now mixes Context documents, registers and feature
groups, and every new register is a breaking change for any bundle that
already used its name for a group.

1.0 reorganises the bundle so it scales and can keep growing:

1. **Features are a register.** Feature documents move into `features/`,
   beside `changes/`, `practices/`, `debts/`, `bugs/` and `releases/`.
2. **The root is closed.** It holds the bundle's own files and the six
   registers, and nothing else, so a later version can add a register without
   colliding with anything.
3. **Every register but `releases/` has one shape.** Documents are filed flat
   or in groups, groups nest to any depth, and one rule says which directory
   belongs to a document.
4. **Feature IDs are full paths**, such as
   `features/payments/instant-refunds`. The definition of an ID does not
   change; features stop being the exception to it.
5. **The default location is `docs/fdf/`.** The name says what the directory
   holds, and leaves the rest of `docs/` to the project.
6. **Versioning from 1.0 on.** A minor version only adds; a major version may
   break, and ships a migration. fdf 1.x validates spec 1.x only.
7. **`fdf migrate` upgrades any 0.x bundle in one run**, including the
   references to it from outside the bundle, after a dry run shows the whole
   plan.

A bug found while designing this is fixed first, as 0.7.1: `fdf mv` breaks the
links that leave the bundle when a move changes a document's depth. Its
corrected link repair becomes the engine that 1.0's moves and migration share.

Not in 1.0: the `Epic` type, which is designed next, as 1.1.

## Evidence

Measured on 2026-09-24.

**Every register so far has cost a migration conflict.**
`scaffold.reservedSince` records the version from which each root directory
stopped being a possible feature group: `releases` (0.2), `changes` (0.5),
`practices` and `debts` (0.6), `bugs` (0.7). 0.7's migrate refuses a bundle
whose feature group is called `bugs/` (`bugsGroupConflict`) until that group
has been moved (`fdf mv bugs <new-group>`).

**ginee**, the dogfood project, has a bundle pinned to 0.6 at
`docs/features/`: 364 Markdown files, 26 features in 2 groups, 7 Changes,
6 Fixes, 14 practices and 33 debts. A read-only simulation of the migration
below measured:

- The root holds 8 files, 5 register directories and the 2 feature groups.
- Moving the groups into `features/` moves 275 of the 364 files.
- Feature IDs appear 176 times in 35 documents, which a reference repair
  rewrites, and 188 times in logs, which keep their words.
- 399 links in 91 files change:
  - 206 written from the bundle root (`/ekpie/…`);
  - 40 relative links into a feature group;
  - 79 from a file that moves to a document that stays;
  - 74 that leave the bundle, such as `../../okf/modules/auth.md` in a
    feature, which needs one more `../`.
- `resource` and `applies-to` values are relative to the project root
  (`ekpie/server/…`), so no move changes them.
- Outside the bundle, 138 git-tracked files mention its path 389 times:
  `CLAUDE.md`, `Taskfile.yml`, `.mise.toml`, READMEs, an ESLint config, and
  code comments citing practices, generated protobuf code included. Among
  them are `/docs/features/…` written from the project root and
  `$PWD/docs/features` in shell snippets. None is inside a URL; 2 follow a
  longer path (`repo/docs/features`, in an old plan).
- 64 Markdown links in 17 files outside the bundle point into it. 19 of them
  never spell its path (`../features/debts/…` from `docs/launch/`), so a text
  search alone would miss them.
- No stray document sits at the root, and no practice, debt or bug shares its
  name with a directory. A document and a directory share a name only in
  `changes/`, where the directory is the task directory.

**`fdf mv` breaks links on a move that changes depth.** Reproduced with fdf
0.7.0: moving `changes/refund-window` to `changes/payments/refund-window`
repaired the links inside the bundle, but left all six links that leave it,
in the Change, its spec and its task, one `../` short. `fdf validate` warned
about five of them. The sixth was a reference definition, which the
validator does not check.

## 1. Layout

```
docs/fdf/
├── INDEX.md                 # pins fdf_version: "1.0"
├── LOG.md
├── SPEC.md                  # the vendored 1.0 specification
├── README.md                # optional, ignored
├── STACK.md  ARCHITECTURE.md  SURFACES.md  INFRA.md  DOMAIN.md
├── features/
│   ├── INDEX.md                          # lists its groups and flat features
│   ├── onboarding.md                     # flat: ID features/onboarding
│   ├── onboarding/01-signup-form.md      # its task directory
│   └── platform/                         # a group
│       ├── INDEX.md
│       └── payments/                     # a nested group
│           ├── INDEX.md
│           ├── instant-refunds.md        # ID features/platform/payments/instant-refunds
│           ├── instant-refunds.spec.md   # .plan.md, .test.md, .surface.md, .log.md as before
│           └── instant-refunds/01-refund-api.md
├── changes/                 # same shape; a Change or Fix owns a task directory
├── practices/  debts/  bugs/                # same shape; they own no directory
└── releases/                # flat: releases/<version>.md
```

**Rules**

1. **The root is closed.**
   - A Markdown file at the root is `INDEX.md`, `LOG.md`, `SPEC.md`,
     `README.md` or one of the five Context documents.
   - A directory at the root that holds Markdown is one of the six registers:
     `features/`, `changes/`, `practices/`, `debts/`, `bugs/`, `releases/`.
   - Anything else is an F3 error that says where it belongs: in a register,
     or outside the bundle.
   - Files that are not Markdown, directories that hold none, and hidden
     files and directories stay outside FDF, as today.
2. **Every register has one shape**, except `releases/`, which stays flat.
   Documents are filed flat or in groups, groups nest to any depth, and one
   register may mix both. Each group SHOULD have an `INDEX.md` that lists its
   documents and subgroups, and any group may have a `LOG.md`.
3. **One directory rule.** A directory beside a document of the same name
   (`<name>/` next to `<name>.md`) belongs to that document.
   - Beside a Feature, Change or Fix, it is the task directory. It holds only
     `NN-<name>.md` tasks, and no directory that holds Markdown.
   - Beside a Practice, Debt or Bug, which own no directory, it is an F3
     error.
   - Every other directory is a group.
4. **No reserved names inside a register.** A feature group may be called
   `bugs` or `changes`. Group names and slugs are `[a-z0-9-]` at every depth.
5. **Indexes.** The root `INDEX.md` pins the version and SHOULD list the
   Context documents and the registers the bundle has. Each register's
   `INDEX.md` lists its top-level documents and groups, and each group's
   lists its own. A command that creates a group lists it in its parent's
   `INDEX.md`.
6. **F12** never scans a register's name as a name the bundle chose, and
   `features` joins that list. Group names and slugs are scanned as before.

Trail roles, statuses and lifecycles do not change. A feature keeps its
`spec`, `plan`, `test`, `surface` and `log` siblings and its task directory; a
Change or Fix keeps `spec`, `plan` and `log`; a practice, debt or bug keeps
only `log`.

### Why flat features

Every other register already takes `<slug>.md` directly. Features were the
exception only because they sat at the bundle root, where a flat feature would
have stood between `STACK.md` and `INDEX.md`. Inside `features/` that reason
is gone. A small project need not invent a `core/` group, and grouping later
is one command: `fdf mv features/onboarding features/accounts/onboarding`.

The cost:

- A flat feature and a group cannot share a name, because the directory would
  be the feature's task directory. `fdf new` refuses the clash.
- A feature ID has two or more segments rather than exactly two, so nothing
  may assume it has a group.
- A register that mixes both shapes can look untidy.

### Why nested groups, in every register

A very large project outgrows one level of groups. Nesting is allowed in every
register rather than in `features/` alone, so that the five registers share
one position rule. That also lets the validator and every command share one
implementation of it (see *CLI*).

### Why a closed root

1. **New registers stop being breaking changes.** A later 1.x can add a
   register knowing that no conforming 1.0 bundle holds Markdown under its
   name. This is what lets a minor version add one (see *Versioning*).
2. **The root stays small at any size**: at most nine files and six
   directories, by rule rather than by habit.
3. **Nothing in the bundle goes unchecked.** 0.7 ignores a stray document at
   the root: nothing validates it, the lexicon never scans it and `fdf mv`
   never repairs it, yet an agent may read it as authoritative. With the
   bundle at `docs/fdf/`, free-form documents belong elsewhere in `docs/`, as
   ginee's `docs/okf/` and `docs/launch/` already do.

### Room for Epic (1.1)

The directory rule decides what a directory holds from the type of the
document beside it. 1.1 can add one case, a directory beside an `Epic` holds
its features, without changing any case 1.0 defines. No 1.0 bundle can
contain an Epic, so the addition breaks nothing.

## 2. IDs

An ID is still the path from the bundle root without `.md`. Features now live
in a register, so their IDs carry its name, as every other document's ID
does.

| Document | 0.7 ID | 1.0 ID |
|---|---|---|
| Feature | `payments/instant-refunds` | `features/payments/instant-refunds`; flat `features/onboarding`; nested `features/platform/payments/instant-refunds` |
| Change, Fix | `changes/payments/refund-window` | unchanged |
| Practice, Debt, Bug | `practices/permission-checks`, … | unchanged |
| Release | `releases/1.2.0` | unchanged |

- **Where feature IDs appear:**
  - the fields `affects`, `retires`, `replaced-by` and a feature's
    `depends-on`;
  - the `## <feature-id>` headings of `# Scenario changes`,
    `# Regression cases` and `# Violates`;
  - the arguments of `fdf history`, `fdf log`, `fdf mv` and `--affects`.
- **Commands that create a document** take its path inside its register, as
  `fdf practice`, `fdf debt`, `fdf bug`, `fdf change` and `fdf fix` already
  do: `fdf new payments/instant-refunds`,
  `fdf adopt --resource … payments/card-payments`.
- **A reference still written the 0.7 way** fails with a hint:
  `affects names payments/instant-refunds — did you mean features/payments/instant-refunds? (F10)`.

**Why full paths.** Every ID says what kind of document it names
(`features/…`, `changes/…`, `bugs/…`). No name is reserved inside
`features/`, and no future register can collide with a feature ID.

Rejected:

- **Feature IDs relative to `features/`.** That makes two ID rules, and
  `bugs/x` could name a bug or a feature in a group called `bugs`. Register
  names would stay reserved as group names, and every new register would
  break someone again.
- **Accepting both forms.** Every reference would have two spellings, which
  grep, `fdf mv` and the lexicon scan would all have to treat as one. That
  goes against FDF's own rule of one name per thing.

The cost is a longer ID and a one-time rewrite, which migrate does. In ginee
that is 176 mentions in 35 documents.

## 3. Location and root resolution

- **The default bundle root is `docs/fdf/`,** resolved against the project
  root. Two things stay as they are: the precedence (`--root`, then
  `FDF_ROOT_DIR`, then the default), and the rules that find the project root
  (topmost `.git`, submodules, linked worktrees).
- **The spec's *Location* section gives the reason:** the directory holds the
  whole bundle, not only its features, and the rest of `docs/` belongs to the
  project's other documentation.
- **Monorepos and submodules** keep their shape at the new path: one bundle at
  `docs/fdf/`, and `<project>/docs/fdf/` for projects that do not link. A
  submodule bundle works as before.
- **fdf 1.x also looks in `docs/features/`.**
  - With no flag or variable set, it uses the first of `docs/fdf/` and
    `docs/features/` that holds an `INDEX.md`. When neither does, it uses
    `docs/fdf/`, where `fdf init` creates a bundle.
  - `docs/features/` counts only when its `INDEX.md`, spelled so, pins
    `fdf_version`. A documentation site may have a `docs/features/` section
    whose `index.md` a disk that ignores case opens as `INDEX.md`; taken for
    a bundle, `fdf init` would send the user to `fdf migrate`, which would
    turn the site's pages into one.
  - An upgraded binary therefore still finds a bundle nobody has migrated:
    `fdf validate` says it pins 0.x and to run `fdf migrate`, `fdf migrate`
    needs no flag, and `fdf init` refuses to create a second bundle beside it,
    as it already refuses an older pin.
  - The header every command prints labels the old location
    `(pre-1.0 default docs/features)`. When both directories hold a bundle,
    `docs/fdf/` wins and the header warns.
  - The spec says a tool MAY look there.

## 4. Versioning

- **This specification is 1.0**, and a bundle pins `fdf_version: "1.0"` in its
  root `INDEX.md`. The pin is required:
  - a root `INDEX.md` without one is an F1 error (0.7 validated an unpinned
    bundle under 0.2 rules, with a warning);
  - a directory without a root `INDEX.md` is not a bundle.
- **A minor version only adds.** 1.1, 1.2 and later may add document types,
  registers, optional fields, soft checks and commands, but never an error for
  something a conforming bundle already has. The closed root is what makes a
  new register safe. A bundle takes up a minor version with `fdf migrate`,
  which bumps the pin, re-vendors `SPEC.md`, creates any new register's
  `INDEX.md`, and edits no document.
- **A major version may break**, and ships a `fdf migrate` from the previous
  major. Errata keep their rule: they only relax.
- **Validators apply what the pinned version defines.** fdf 1.3 checks a 1.0
  bundle as 1.0, and a type that 1.1 introduces is an error in a bundle pinned
  to 1.0 until its pin moves. Upgrading the CLI never changes a result, and
  moving the pin never breaks a conforming bundle.
- **One CLI major per spec major.**
  - fdf 1.y validates bundles pinned to 1.0 through 1.y, and migrates any
    0.x bundle (0.1 to 0.7) straight to 1.y. It does not validate 0.x.
  - A pin it cannot validate gets an F1 error that names the fix:
    `fdf migrate` for an older major, a newer fdf for a newer minor.
  - As today, fdf X.Y.z ships spec X.Y as current.
- **The 0.x specification texts stay in `spec/`** as history. `fdf spec -v
  0.7` still prints one, for reading an old vendored copy.

## 5. Link repair (the prerequisite, in 0.7.1)

**Root cause.** `(*plan).retarget` (`cli/internal/refactor/mv.go:483`) returns
early for any link that resolves outside the bundle. That is right when the
linking file stays put: its target does not move, so there is nothing to
repair. It is wrong when the linking file moves, because its relative path to
the unmoved target changes. The migrate package repeats the same rule in
`rewriteCasingLinks` (`migrate.go:563`) and `rewriteLinksAfterMoves`
(`migrate.go:784`).

**The rule.**
- A relative link is recomputed whenever its source file moves or its target
  moves, wherever the target is.
- A target outside the bundle keeps its place in the project. The new link is
  its path from the source's new directory, keeping any fragment, query and
  trailing slash.
- A link written from the bundle root changes only when its target moves.
  URLs and in-page anchors never change.
- Inline links and reference definitions are both repaired.

**Delivery.**
- The fix ships first as 0.7.1, queued as its own task, so that a 0.7 user
  moving documents today is not hurt.
- In 1.0 the corrected logic becomes the one link-repair engine that `fdf mv`
  and `fdf migrate` share, replacing migrate's own rewriters.
- The validator's broken-link soft check reads links the way the engine does,
  reference definitions included, so it checks exactly the links the engine
  repairs.

## 6. `fdf migrate`: any 0.x bundle to 1.0

```
fdf migrate [--root <dir>] [--dry-run] [--to <dir>]
```

**Principle.** Migrate works out the finished result before it writes
anything, then either prints the plan (`--dry-run`) or applies it. For a
0.1–0.3 bundle it runs the existing layout steps on a scratch copy, so a bundle
at any pin gets a complete preview.

### What it does, in order

1. **Older layouts become 0.7-shaped**, by today's steps: 0.1's case renames,
   0.3's trail lift, and 0.7's removal of the status tags in index listings.
2. **Feature groups move into `features/`.**
   - Every root directory that is not hidden, holds Markdown, and is not
     reserved by the bundle's pin (`scaffold.reservedSince`) is a feature
     group.
   - It moves with everything in it: trails, tasks, `INDEX.md`, `LOG.md`,
     images.
   - A directory with no Markdown stays where it is, outside FDF.
   - A 0.6 bundle's `bugs/` group becomes `features/bugs/`, so 0.7's refusal
     (`bugsGroupConflict`) goes.
3. **Feature IDs gain `features/`.**
   - This is a reference repair, a maintenance edit, so it reaches frozen
     documents too: reference fields, declaration headings, and mentions in
     prose and code spans.
   - Logs keep their words and only their links are repaired, as after any
     move.
   - No `timestamp` changes.
4. **Links are repaired** in one pass by the engine in *Link repair*:
   relative links, links written from the bundle root (`/ekpie/…` becomes
   `/features/ekpie/…`), reference definitions, and links that leave the
   bundle.
5. **Indexes.**
   - `features/INDEX.md` is created.
   - Each group's listing moves there from the root `INDEX.md`, description
     and all. Listings move with what they list, as they do in `fdf mv`.
   - The root gets `[Features](features/INDEX.md)` where the first group
     listing stood. A group the root never listed gets a generated listing.
   - The other registers' indexes are created as today.
6. **Pin, spec and stubs.** The root pins `fdf_version: "1.0"`, `SPEC.md` is
   re-vendored, and any missing Context stub is created.
7. **Relocation.**
   - A bundle at `…/docs/features/` moves to `…/docs/fdf/` beside it,
     however it was found. That includes `<project>/docs/features/` in a
     monorepo.
   - A bundle anywhere else stays where it is.
   - `--to <dir>` picks the destination instead. Naming the current path
     keeps the bundle where it is.
   - A plain directory is renamed. A submodule is moved with `git mv`, which
     updates `.gitmodules`.
8. **References outside the bundle** are rewritten in the project's
   git-tracked text files. Binary files are skipped.
   - **Links.** A Markdown link that resolves into the bundle is retargeted,
     whether or not it spells the bundle's path (`../features/debts/…` from
     `docs/launch/`).
   - **Path mentions.** A mention of the bundle's path is rewritten, longest
     match first:
     - `docs/features/practices/amounts.md` → `docs/fdf/practices/amounts.md`
     - `docs/features/ekpie/x.md` → `docs/fdf/features/ekpie/x.md`
     - a bare `docs/features` → `docs/fdf`
   - **Where a mention counts:** where a path begins, which is at the start of
     a word, after a `/`, `./` or `../` that begins the path, or after a
     variable or placeholder (`$PWD/`, `${ROOT}/`, `<worktree>/`).
   - **Mentions left alone and listed:** one inside a URL, because a
     permalink has to keep the old path; and one after a longer path
     (`repo/docs/features`), because that may name another bundle.
   - **Skipped: what `fdf install` manages**, meaning the primer section in
     agent instruction files and the installed fdf skills. Install replaces
     them whole, and a rewritten copy would read as a user edit and block the
     upgrade.
   - **Not touched: bare feature IDs outside the bundle.** There,
     `ekpie/cancel-order` cannot be told apart from a code path like
     `ekpie/server/…`.
   - **Inside the bundle, the same path-mention rule applies** (a Context
     document's `--root docs/features`, a task citing
     `docs/features/practices/…`), except to the words of logs. Like the ID
     rewrite, it is a reference repair after a move.
   - Afterwards, every remaining occurrence of the old path is listed, so
     nothing stays behind silently.
   - Outside a git repository nothing outside the bundle is searched, and
     migrate says so.
9. **Log, validate, next steps.**
   - One entry in the root `LOG.md` records what moved, with counts.
   - The bundle is validated. Unfilled Context stubs are reported as
     warnings, as today, and a bundle older than 0.7 also gets 0.7's
     findings.
   - Migrate then prints the next steps:
     - `fdf install`, because the skills and primer still describe 0.7;
     - review with `git diff -M`, then commit, starting inside the submodule
       if the bundle is one;
     - a note to change `FDF_ROOT_DIR` when it still names the old path.

### Refusals

Checked before anything is written; the bundle and the project are left as
they were.

- **A Markdown file at the root with no place in 1.0.** 0.7 ignored these;
  move it out of the bundle or into a register.
- **A practice, debt or bug that shares its name with a directory beside
  it.**
- **A destination that exists and is not empty,** unless it is the bundle's
  current path.
- **Uncommitted changes in any file migrate would write, or untracked files
  in the bundle.** Git is the undo, and a diff that mixes someone's edits with
  migrate's cannot be cleanly reviewed or reverted. Outside a git repository
  there is no check.
- **A pin newer than this fdf knows,** and the existing 0.1–0.3 pre-flight
  checks.

### Dry run

A summary, then every file it would move or edit, with counts. For ginee:

```
plan: fdf_version 0.6 → 1.0 (dry run: nothing changed)
  bundle     docs/features/ → docs/fdf/
  features   ekpie/, jibeka/ → features/          (26 features, 275 files)
  ids        176 mentions in 35 documents; logs keep their words (188)
  links      399 in 91 files
  indexes    features/INDEX.md: 2 listings moved from INDEX.md
  outside    389 mentions in 138 files; 64 links in 17 files
             left as they are: 2 mentions after a longer path (listed below)
```

### Re-runs and failures

- A bundle already at 1.0 takes today's repair path: the spec copy, indexes
  and stubs are restored, and nothing moves.
- If applying fails partway, the clean-tree rule means `git checkout` and
  `git clean` on the listed paths restore everything. Migrate prints the exact
  commands.

## 7. CLI

### One source of layout knowledge

A new package, `cli/internal/layout`, answers every question about positions:
- the root's reserved files and its registers;
- the directory rule;
- a path's ID, and an ID's path;
- where a new document of each type goes.

The validator, the scaffolding commands, `mv`, `lexicon`, the registers,
`adopt`, `history`, `release`, `log` and `migrate` all ask it.

Why: today each command carries its own copy of which directories are
reserved, what is a group and what is a task directory. Several recent fixes
were a command disagreeing with the validator about exactly that (cbcb4c3,
4ebbd88, ce53c07, df8a36d). Every command changes for 1.0 anyway.

### Command by command

| Command | In 1.0 |
|---|---|
| root resolution (`fdfroot`) | `docs/fdf` by default; also looks in `docs/features/`; the header labels which location it used, and warns when both hold a bundle |
| `validate` | 1.0 rules only, so every 0.x version gate goes. Position checks come from `layout`. Adds the closed root, nested groups and flat features. F1 requires a pin. Adds the did-you-mean hint. F12 skips `features` |
| `init` | also creates `features/INDEX.md`; the root `INDEX.md` lists the Context documents and the registers |
| `new`, `adopt`, `practice`, `debt`, `bug`, `change`, `fix` | take `[<group>/…]<slug>`. Create any missing group at any depth and list each in its parent's `INDEX.md`. Refuse a name that clashes with a document or group beside it |
| `change`, `fix`, `bug` (`--affects`); `history` | take full feature IDs; scaffolded declaration headings read `## features/…` |
| `mv` | uses the shared link engine, at any depth, flat to grouped and back, and between registers as today |
| `lexicon`, `log`, `release`, `debt --cleanup`, `bug --cleanup`, `adopt` (map) | get IDs and group depth from `layout`; cleanup removes a group left empty at any depth |
| `migrate` | as in *`fdf migrate`* above |
| `install` | the primer and skills describe 1.0, and today's primer joins `legacyPrimers`. An untouched 0.7 primer is recognized whether it was written for `docs/features` or the new root, because install reads the root recorded in `.fdf-version`. An upgrade therefore replaces it instead of keeping it as a user edit |
| `help` | every usage line and example is updated in `helpTopics`; `help_test` still checks that every flag is documented |
| `spec` | prints 1.0; `-v 0.x` still prints the old texts |
| `serve` | only its root resolution changes |

**Version handling.** `CurrentVersion` becomes `"1.0"`, and pin comparison
parses `MAJOR.MINOR`; `pinAtLeast` assumes `0.x` today.

## 8. Skills and docs

- **All ten skills:**
  - `docs/fdf/` and `features/<group>/<slug>` paths, and `features/` in every
    ID example;
  - flat and nested groups, and the closed root (free-form documents live
    outside the bundle);
  - the upgrade: `fdf migrate`, then `fdf install`;
  - fdf-checkpoint, when it audits the vendored `SPEC.md`, sends a 0.x pin to
    `fdf migrate`;
  - the trigger descriptions of fdf-help and fdf-validate name `docs/fdf/`.

  No new skill arrives in 1.0.
- **`spec/1.0.md`** starts from `0.7.md`:
  - Structure, Location, Casing, Types, F1 and F3 are rewritten, and every
    example path gains `features/`;
  - *Which rules apply to which version* is replaced by the 1.x versioning
    policy, *Upgrading from 0.x* (what migrate does) and *Changes from 0.7*;
  - every other rule carries over unchanged.
- **`SPEC.md` and `spec/README.md`:** 1.0 is current, and the 0.x versions are
  marked "not validated by fdf 1.x; upgrade with `fdf migrate`".
- **`README.md`:** the new layout and commands, and an *Upgrading to 1.0*

## Rule changes

| Rule | Change in 1.0 |
|---|---|
| F1 | The pin is required. A 0.x pin is an error pointing at `fdf migrate`; a newer 1.x pin is one pointing at a newer fdf. (0.7: a missing pin was a warning, and meant v0.2 rules.) |
| F3 | The closed root; features under `features/`, flat or in groups; groups nested to any depth in every register except `releases/`; the directory rule, including its error beside a practice, debt or bug; no reserved names inside a register |
| F10, F14 | Feature IDs are full paths. A 0.7-style ID gets a did-you-mean hint; only the message changes, not the rule |
| F12 | `features` joins the register names that are never scanned as names |
| Soft checks | "A root `INDEX.md` with no `fdf_version`, or no root `INDEX.md`" is removed, because both are now errors. The broken-link check also reads reference definitions |

Every other rule, the trail, the statuses and the lifecycles are unchanged.

## Decisions

Decided 2026-09-24:

1. **1.0 is a breaking version.** fdf 1.x validates spec 1.x only, and
   `fdf migrate` upgrades any 0.x bundle. Rejected: validating 0.x alongside
   1.0; validating 0.x read-only.
2. **Migrate rewrites references outside the bundle,** after a dry run shows
   them. Rejected: reporting only; an opt-in flag.
3. **Feature IDs are full paths.** Rejected: IDs relative to `features/`;
   accepting both forms.
4. **Flat features** are allowed beside grouped ones.
5. **Groups nest to any depth,** in every register except `releases/`. This
   was proposed for `features/` and extended so that the registers share one
   rule.
6. **The root is closed,** to files and directories. Rejected: closing
   directories only; leaving the root open.
7. **Epic arrives in 1.1** and is designed next; 1.0's directory rule leaves
   room for it. Rejected: designing it into 1.0; relying on nested groups
   alone.
8. **`docs/fdf/` is the default,** and fdf 1.x still finds a bundle at
   `docs/features/`.
9. **Versioning:** minors only add, majors break and ship a migrate,
   validators apply the pinned version, and one CLI major serves one spec
   major.
10. **Migrate's safeguards and options:** it plans first, with `--dry-run`;
    it refuses on uncommitted changes; it moves `…/docs/features/` to
    `…/docs/fdf/` unless `--to` says otherwise; and it moves a submodule with
    `git mv`.
11. **The `fdf mv` link fix ships first,** as 0.7.1.
12. **One `layout` package** is the single source of positions and IDs.

## Out of scope

- **Epic** (1.1).
- **Moving the Context documents:** they stay at the root.
- **Rewriting bare feature IDs or URLs outside the bundle:** they are listed
  or left alone, never rewritten.
- **Rewriting the words of logs:** only their links are repaired.
- **Any other rule change:** the trail, the statuses and the lifecycles, and
  F2, F4 to F9, F11 and F13 stay as 0.7 has them.
- **Validating 0.x bundles** with fdf 1.x.
- **Groups in `releases/`.**
- **`fdf where <path>`,** the reverse lookup 0.7's design proposed as a
  follow-up.
