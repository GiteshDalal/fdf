# FDF v0.7 — bugs, one vocabulary everywhere, refactoring, and adoption

**Date:** 2026-09-23
**Status:** approved 2026-09-23 (decisions 1–3 as recommended; names as proposed)

## Summary

v0.7 closes four gaps that show up as soon as FDF is used on a real codebase:

1. **Bugs have no home.** A known defect nobody is fixing yet can only be filed as
   a `Debt`. v0.7 adds a `Bug` register (`bugs/`, `type: Bug`).
2. **The lexicon stops at the Gherkin.** F12 checks features and declared scenario
   names only, so specs, plans, tasks and logs keep the old words forever. v0.7
   scans every document except `slug.test.md` and `slug.surface.md`, which quote
   what a surface shows.
3. **Renaming is manual.** Renaming a feature means hand-editing its trail, every
   `affects:`, every link and every declaration heading. v0.7 adds `fdf mv` and
   `fdf lexicon`, and makes the edits they perform — *maintenance edits* — legal
   on frozen documents.
4. **Existing code cannot be documented honestly.** A capability that predates the
   bundle can only be `done` with an invented spec, plan and tasks, or `draft`,
   which blocks every Change and Fix. v0.7 adds the `adopted` feature status and
   a phased adoption workflow.

## Evidence

Every claim below was measured, not assumed.

**The 0.6 validator leaves Debt as the only legal home for a defect that is not
being fixed right now.** A draft `Fix` with no `affects` fails F10 (`requires a
non-empty affects`). A draft `Fix` against an undelivered feature fails F10 (`a
feature that is not delivered is edited directly`). The same defect filed as a
`Debt` passes. So a defect in code no feature documents, a defect not yet
diagnosed, and a defect deferred in an in-flight feature can only be debts.

**The 0.6 validator has no honest status for existing code.** An existing
capability documented as `done` fails F4 three times (spec, plan, ≥1 task) and F8
once. The same document as `draft` passes, but then the first `Change` against it
fails F10 (`affects names … with status 'draft'`). The only passing routes are an
invented build history, or a draft that routes to fdf-brainstorm as if the
capability had not been built.

**A real v0.6 bundle** (the dogfood project: 26 features, 11 Changes and Fixes,
32 debts, 13 practices, about 450 RPCs in the codebase) shows all four gaps:

- **Debts that are bugs.** About 12 of the 32 debts describe the software doing
  something observably wrong. Their authors put a symptom, a caveat about
  whether it can be reached, related features (as prose links) and the open
  question of what should happen instead under `# Gap` and `# Cost`, because
  Debt has no other slots.
- **Vocabulary drift F12 cannot see.** `fdf validate` reports **0** F12 findings:
  every feature's Gherkin was swept when the lexicon was adopted. A scan of every
  document with the masking proposed below (code spans, code blocks, link
  targets, URLs and comments are not scanned; `slug.test.md` and
  `slug.surface.md` are excluded) reports **2,534 banned-word hits in 248 of 329
  documents**. 84% are in episodic documents: specs, tasks, plans, logs, changes.
  - **Mostly real drift, about half.** Five words account for 1,358 hits: the old
    names of three renamed terms already swept out of the Gherkin (871, 195, 168)
    and two banned synonyms (78, 46).
  - **Other senses, about 10%.** Collision words: git *branch* (83), *integration*
    tests (64), container *registry* (48), *resolver* (44).
  - **Mixed, about 28%.** *line* (599) means a sale's entry and also a log line or a
    code line; a rough classifier puts about 145 as log or code lines and the rest
    as the renamed concept. *agent* (107) means the banned role and also an AI
    agent.

  Taken together, roughly 70% of the hits are real drift that 0.6 cannot see.
  The noise sits in a handful of words, and most of it disappears once the word
  is qualified ("git branch", "log line", "AI agent").
  - **Paths.** 13 document paths use a banned word themselves, 9 of them task
    files.
- **An adoption gap.** 26 features against about 450 RPCs in 34 services. One of
  the 20 backend modules is never named anywhere in the bundle, and several are
  named only once.

## Foundation: maintenance edits

0.6 allows exactly one edit on every document, episodic ones included: the
lexicon fix. v0.7 generalizes it into a class.

> A **maintenance edit** substitutes one name for another according to a recorded
> mapping, and changes nothing else. It is allowed on every document, living or
> episodic, at any status, and it is logged.

| Maintenance edit | The mapping | Logged in |
|---|---|---|
| **Lexicon fix**: a banned word replaced by its term | `DOMAIN.md` | root `LOG.md` |
| **Reference repair**: a document's ID, and every link and edge to it, updated after a move | the move | root `LOG.md` (written by `fdf mv`) |
| **Path repair**: a `resource:`/`applies-to:` path updated to where the code now lives | the code move | the owning document's log |

This is what makes `fdf mv` and `fdf lexicon --fix` legal. Their edits reach frozen
specs, plans, tasks and finished changes, and they change no fact about the
work. It also makes normative the R1 path-repair rule that today exists only in
the fdf-validate skill. The 0.6 sentence "renaming a document is a move, not a
word fix" stays true. v0.7 simply defines what a move is allowed to touch.

Anything else on an episodic document is still not allowed: new work gets a new
episode.

## 1. Bugs — a register of known defects

### Why a new type, not `Debt` with a `kind:` field

- **One name per concept is FDF's own rule.** A bug filed as "debt" is exactly
  the synonym drift `DOMAIN.md` exists to stop, inside FDF's own vocabulary.
- **The invariants differ.** A bug states expected behavior and may cite the
  scenarios it contradicts. An *accepted* bug must not contradict a living
  scenario (below). FDF separates types whose invariants differ; it keeps
  `Change` and `Fix` apart for this reason rather than adding a discriminator
  field.
- **The repair routes differ.** A debt's repair is usually plain code work, such
  as bringing code into line with a practice. A bug's repair changes observable
  behavior, so it goes through a `Fix` or `Change` with a regression case. If
  both lived in one register, an agent could "pay down" a bug with plain code
  work and no test, and the bug would return.
- **A draft `Fix` is not a register.** It needs `affects:` naming delivered
  features and a settled Fix-vs-Change decision. A bug report comes before both
  (see *Evidence*). It also has no honest way to say "won't fix".

**The dividing line** — for skills and humans alike:

> Can someone observe the software doing something wrong? → **Bug**, even when a
> practice violation is its root cause.
> Is the code short of what the project says, with nothing observably wrong
> (unfinished work, a practice not followed everywhere, missing tests, dead
> code)? → **Debt**.

### Shape

`bugs/<slug>.md` or `bugs/<group>/<slug>.md` (`type: Bug`). The directory has the
same shape as `debts/`: an `INDEX.md`, one level of groups, and `<slug>.log.md`
as the only legal sibling. There are no tasks: a bug is a register entry, not a
unit of work.

| Status | Invariant |
|---|---|
| `open` | The defect exists. `# Violates`, when present, names scenarios that exist |
| `accepted` | Kept deliberately (won't fix). Requires `# Rationale`. **Must not carry `# Violates`**: a scenario the project knowingly and permanently contradicts is a document that lies. Fix the code (`Fix`) or change the promise (`Change`) |
| `resolved` | Closed. Requires `# Resolution` naming what closed it: the Fix or Change whose `resolves` names the bug, or why nothing needed repairing (not a defect, a duplicate, the code is gone). A bug that still carries `# Violates` is closed only by a done Fix or Change that resolves it |

Frontmatter: `affects` (optional: the related features, each existing; must
include every `# Violates` heading) and `resource` (optional, R1, warned when
absent on an open or accepted bug, as for debts).

Body:

- `# Symptom` — **required**. What the software does wrong, with evidence: a
  reproduction (command and output) or, for a defect found by reading, the code
  path and the input that reaches it. Say which one it is.
- `# Expected` — **required**. What should happen instead. Either cite the
  scenario that already says so, or state that no document decides it and name
  the open question. The second case makes the repair a `Change`, because
  someone has to decide.
- `# Violates` — optional, parsed. `## <feature-id>` followed by
  `- <scenario name>`, names verbatim. If present, the bug is Fix-class.
- `# Root cause`, `# Cost` — optional. `# Cost` is the same heading a debt uses.
- `# Rationale` (accepted), `# Resolution` (resolved).
- No Gherkin.

```markdown
---
type: Bug
status: open
title: Refunds past midnight UTC land on the wrong day
affects: payments/instant-refunds
resource: [internal/payments/refund.go]
timestamp: 2026-09-23
---

# Symptom

A refund made at 23:30 in Sydney is reported in the next day's totals.
Reproduce: `go test ./tests -run TestRefundDayBoundary` (fails: got 2026-09-24).

# Expected

The refund counts on the Venue's local day, as the scenario below already says.

# Violates

## payments/instant-refunds

- Refund is reported on the Venue's local day
```

### Lifecycle around the work

fdf-debug diagnoses the bug. If it is repaired now, it routes to a Fix, Change or
task, as today. If it is not repaired now — undiagnosed, in undocumented code,
waiting on a decision, or deferred — everything learned goes into a Bug.

When a Fix or Change repairs it, the analysis moves into that document, which is
the permanent episodic record (`fdf fix --from bugs/<id>` prefills `affects`,
`# Symptom`, `# Root cause` and the regression-case names from `# Violates`).
The bug flips to `resolved` with a `# Resolution` naming it. `fdf bug --cleanup`
then folds it into `bugs/LOG.md`, exactly as `fdf debt --cleanup` does. No edge
points at a bug, so cleanup never breaks a reference.

### Rule F14 — Bug integrity

Bugs appear only under `bugs/`. Status is one of the three above. `# Symptom`
and `# Expected` are non-empty. There is no Gherkin. An accepted bug has
`# Rationale` and no `# Violates`. A resolved bug has `# Resolution`. While a
bug is open, every `# Violates` name exists verbatim in its feature and every
heading is in `affects`.

### CLI

- `fdf bug [--open|--accepted|--resolved] [--cleanup [--dry-run] [--no-log]] [[<group>/]<slug>]`
  mirrors `fdf debt`; both run on one shared register implementation.
- `fdf history <feature>` also lists the open bugs whose `affects` names the
  feature.

### Existing debts that are bugs

Migration moves nothing. fdf-checkpoint proposes re-filing each defect-shaped
debt, and `fdf mv debts/<id> bugs/<id>` re-files one: the type flips and
`# Gap` becomes `# Symptom`. `fdf validate` then asks for `# Expected`, the one
piece of analysis the debt never had to state.

## 2. Domain language in every document

### Scope

F12 scans **every document** except four:

| Excluded | Why |
|---|---|
| `SPEC.md` | Vendored reference; its examples use someone else's vocabulary |
| `DOMAIN.md` | It names the banned words by necessity |
| `slug.test.md` | Verifications quote literal output: error strings, labels, URLs |
| `slug.surface.md` | Surface wording, which `SURFACES.md` governs, not the lexicon |

`SURFACES.md` **is** scanned. When it maps a term to a label, it quotes the label
in a code span ("a Venue is shown to merchants as `Store`").

Inside a scanned document, text that **quotes** rather than **chooses** is not
scanned:

- code spans;
- fenced blocks other than ```` ```gherkin ````;
- link targets and bare URLs;
- HTML comments;
- double-quoted text outside Gherkin;
- a declaration's `## <feature-id>` headings and a regression case's
  verification (unchanged from 0.6).

In frontmatter, `title`, `description` and `tags` are scanned; ID, path and enum
fields are not. **Document and directory names** are scanned as
hyphen-delimited tokens. The fix for a banned word in a name is `fdf mv`.

The code-span convention is not new. FDF already treats a link inside code as
sample text, and this extends that reading: code means *quoted*. A mention of a
banned word (for example, a log entry recording that `store` was renamed to
Venue) goes in a code span.

### `except:` — say which thing you mean

The measured noise is concentrated in words with a second, technical sense:
*branch*, *integration*, *registry*, *line*, *agent*. v0.7 adds one lexicon
bullet:

```markdown
## Venue
A physical location where a merchant sells.
- instead-of: store, shop, branch
- except: data store, git branch
```

An `except:` phrase is one where a banned word means something else. It is
masked everywhere before the scan, the same way a canonical term is masked
today. Each phrase must contain one of its term's banned words **plus at least
one other word**, which is an F12 lexicon-consistency error otherwise. A bare
word would silently un-ban itself.

This is a writing rule as much as a checker rule. Where a banned word means
something else, qualify it ("git branch", "AI agent", "log line", "integration
test"). The qualified phrase is clearer to a human reader too, and it is what
`except:` lists.

### Severity and output

Findings stay **warnings** by default and become errors under `--strict-domain`,
as in 0.6. New: `DOMAIN.md` may declare `strict: true` in its frontmatter, so the
bundle itself turns strictness on and every `fdf validate` (local, CI, and
agents) enforces it without anyone remembering a flag. Setting it is a
`DOMAIN.md` edit, so it needs approval and a log entry like any other.

Because the first run after migrating can report hundreds of documents,
`fdf validate` prints F12 **one line per document** (the words and their counts)
and at most 20 documents. The rest are summarized in one line that points at
`fdf lexicon` for the full report. The exit code still reflects every finding.

## 3. Refactoring: `fdf mv` and `fdf lexicon`

### `fdf mv [--dry-run] <from> <to>`

Moves or renames a document together with its whole trail, and repairs every
reference to it (a maintenance edit).

- **What it moves.** A feature `<group>/<slug>` with its spec, plan, test,
  surface and log siblings and its task directory; a whole group; a change or
  fix; a practice; a debt; a bug; or a task within its task directory (rename or
  renumber). It also re-files a debt as a bug and back, the one cross-type move
  (the type follows the position).
- **What it rewrites, in every bundle document, episodic ones included:**
  - markdown links, bundle-relative and relative, keeping their style and
    fragments (a link inside code is a sample and is left alone);
  - frontmatter edges: `affects`, `retires`, `replaced-by`, feature
    `depends-on`, `superseded-by`, and task `depends-on` for task renames;
  - `## <feature-id>` headings in Change, Fix and Bug declarations;
  - `see:` entries in `DOMAIN.md`;
  - plan `# Tasks` links and release lists;
  - ID mentions in text.

  The listing line moves from the old group's `INDEX.md` to the new one's. Log
  entries keep their words, because they record history, but their links are
  repaired.
- **What it refuses:** any destination file that already exists (a stray
  sibling included), an unknown source, Context and reserved files, a merge
  into an existing group, and any cross-type move other than debt↔bug.
- **After the move** it writes one root `LOG.md` entry
  (`**Moved**: payments/store-hours → venues/opening-hours`). It lists
  references *outside* the bundle that still name the old path (such as
  `CLAUDE.md` or code comments) without editing them. It runs `fdf validate`
  last.

`--dry-run` prints every file move and every per-file rewrite, and changes
nothing.

### `fdf lexicon [--term <Term>] [--fix [--dry-run]]`

The command for maintaining domain language.

- **Report (default).** Every F12 finding with `file:line:col` and its context,
  grouped by banned word with counts and the term it maps to. It also lists
  paths that use a banned word, each with a suggested `fdf mv` command. This is
  the triage view.
- **`--fix`** applies the lexicon fix to text:
  - replaces each finding with its term, in the canonical spelling, keeping
    plurals, adjusting a/an, and capitalizing at a sentence start;
  - renames scenario names **atomically across their joins**: the Gherkin,
    `slug.test.md` headings (the file is excluded from the scan but still part
    of the join), task acceptance, and Change, Fix and Bug declarations;
  - writes one `LOG.md` entry.

  `--dry-run` shows the diff first. `--fix` requires `--term`: a sweep
  covers one term at a time. A blind sweep of the dogfood bundle rewrote git
  *branches* and AI *agents* into domain terms, and one term at a time keeps
  each diff small enough to review.
- **What `--fix` leaves alone:**
  - **Paths.** It reports them, and a person chooses the new name. An
    automatic `02-menu-from-catalog` → `02-catalog-from-catalog` shows why.
  - **Italicized occurrences** (`*store*`), which are most often mentions. It
    lists them to be put in code spans.

**The honest limit.** No tool can tell a use of a word from a mention of it or
from another sense of it. The order is therefore: report → triage (qualify and
add `except:`, put mentions in code spans) → `--fix` → review the diff. On the
dogfood bundle that turns about 1,400 real occurrences from impossible by hand
into one reviewed sweep.

**Renaming a term** (for example Venue → Location) is an approved `DOMAIN.md`
edit: a new heading, with the old name moved into `instead-of`. It is followed by
`fdf lexicon --fix --term Location`.

## 4. Adopting existing code

### The `adopted` status

A new feature status for a capability that predates its document: documented
from the code, not built through FDF.

| | `adopted` |
|---|---|
| Build trail | **None**: no `slug.spec.md`, no `slug.plan.md`, no task directory (F4). Adoption records what exists; it built nothing, so it never invents a history |
| `resource` | **Required** (≥ 1 path, R1). The code it documents. A built feature links its code through its tasks; an adopted one has no tasks |
| Scenarios | **Zero or more.** A `Feature:` block alone is a valid *map entry* (F5 relaxed for `adopted`) |
| `slug.test.md` | Required from the first scenario, with one case per scenario (F8). Verifications point at existing tests or explicit manual procedures |
| Delivered? | Yes. `affects:` on a Change, Fix or Bug accepts `adopted` (F10) |
| Lifecycle | `[*] → adopted → retired`. It never becomes `done`: rebuilding it is a Change |

**Backfill.** Adding a scenario to an adopted feature in place is allowed only
when the scenario describes behavior the code already has. The proof is that its
new test case passes against unchanged code, in the same edit. Backfill only
adds: modifying or removing a scenario is a Change, exactly as for `done`.

**Retirement.** F4 changes "`retired` requires `slug.spec.md`" to "…when the
feature has a `slug.plan.md` or a task directory". A feature that was built
keeps its record; one that was adopted never had one.

### Phases

The new **fdf-adopt** skill runs in four phases:

1. **Map (breadth first).** Survey the entry points: routes and RPCs, commands,
   jobs, screens, events. Propose groups and capabilities, approve them in
   batches, and scaffold each as a map entry with
   `fdf adopt --resource <paths> <group>/<slug>`, which gets its `Feature:`
   block and no scenarios. That gives agents a complete map in hours rather
   than weeks.
2. **Backfill on touch.** Before a Change to an adopted capability, backfill
   only the scenarios it will `modify:` or `remove:`; an `add:` needs none. A
   capability with no map entry is mapped before it is changed.
3. **Backfill by risk.** Money, authorization and data loss first, then the
   paths agents touch most (git churn by path ranks them).
4. **Steady state.** New capabilities go through the normal lifecycle.

Rules while backfilling:

- Document **current** behavior, never desired behavior. A scenario is
  backfilled only with a verification that passes today.
- Wrong behavior found while backfilling is a **Bug**. It is never enshrined in
  a scenario and never fixed in the Gherkin.
- A defect in an adopted capability that no scenario covers routes to a
  **Change**: the document was never written, so someone decides now. For an
  obvious case the design gate is a one-line approval.
- Adoption is for code that predates the capability's first document. Using it
  to skip the design gate for code written last week is the vibe coding FDF
  exists to stop.

### `fdf adopt`

- With a slug, it scaffolds an adopted feature.
- Without one, it prints the **adoption map**:
  - each feature with its status (built or adopted), scenario count and tested
    count;
  - totals: built, adopted with scenarios, and map-only;
  - **code no document claims**: `git ls-files` outside the bundle, grouped to
    `--depth N` directories, keeping those that no feature, task, change or fix
    `resource` covers.

  The last list is the "what's left" for planning phases. It is a heuristic,
  and the output says so.

## Rule changes

| Rule | v0.7 change |
|---|---|
| F2 | Feature status gains `adopted`; Bug statuses `open`/`accepted`/`resolved` |
| F3 | `bugs/` positions (same shape as `debts/`); `Bug` only there; `bugs` becomes a reserved root directory name |
| F4 | `adopted` invariants (no build trail, `resource` required); `retired` requires a spec only when a plan or task directory exists |
| F5 | An `adopted` feature may have zero scenarios |
| F8 | Applies to `adopted` from the first scenario |
| F10 | `affects` accepts `adopted` |
| F12 | Scope: every document except `SPEC.md`, `DOMAIN.md`, `slug.test.md` and `slug.surface.md`, plus document and directory names; quoting masks; `except:` grammar and its consistency check; `strict: true` on `DOMAIN.md`; per-document output capped at 20 |
| F14 | **New:** Bug integrity |
| R1 | Also checks `resource` on adopted features and on bugs |
| Text | *Maintenance edits* replace "one edit is allowed on every document"; living/episodic table updated (Bug is living) |

## Migration 0.6 → 0.7

The migration is additive and nothing moves: the pin changes, `SPEC.md` is
re-vendored, and `bugs/INDEX.md` is scaffolded.

- **Pre-flight.** If a feature group is already called `bugs/`, the migration
  refuses with the fix: `fdf mv bugs <new-group>`.
- **What a bundle notices** is F12's wider scope. It shows up as warnings, or
  as failures for projects that run `--strict-domain`. `fdf migrate` prints the
  F12 count and the next step (`fdf lexicon`).
- **Existing debts** stay debts until fdf-checkpoint proposes re-filing the
  defect-shaped ones.

## Skills and docs

- **fdf-help.** New routing rows: "code exists but no feature" → fdf-adopt, and
  "known defect not being repaired now" → file a Bug. Its register checks
  become `fdf debt --open` **and** `fdf bug --open`.
- **fdf-debug.** When not repairing now, file a Bug with the investigation.
  Phase 1 checks both registers.
- **fdf-change.** Supports `--from bugs/<id>`; resolve the bug when the work
  lands.
- **fdf-validate.** Covers the new F12 scope with its triage order (qualify and
  `except:`, code-span mentions, then `fdf lexicon --fix`), F14, and the F4
  rules for `adopted`.
- **fdf-checkpoint.** Its vocabulary check runs `fdf lexicon` instead of a
  hand-built grep, and it re-files defect-shaped debts.
- **fdf-init.** Hands off to fdf-adopt.
- **New:** the fdf-adopt skill.
- **Shipping chores.** Update the primer (appending the 0.6.3 text to
  `legacyPrimers`), add the new skill to `skillNames`, and update the README and
  the plugin manifest.

## Implementation order

1. `spec/0.7.md` (from 0.6 plus the above), plus `spec/README.md` and `SPEC.md`.
2. Validator: a `specV7` gate, `bugs/` and F14, `adopted`, and F12 (scope,
   masks, names, `except:`, `strict`, capped output). Fixtures for every new
   rule: they are the conformance contract.
3. A shared register package, then `fdf bug`, `fdf adopt`, `fdf history` with
   bugs, and `--from` on `fdf fix`/`fdf change`.
4. `fdf mv`, then `fdf lexicon`, which reuses mv's reference machinery and
   F12's scanner.
5. `fdf migrate` 0.6 → 0.7.
6. Skills, primer and README. Test-drive them with the fdf-engineer agent on a
   *copy* of the dogfood bundle: re-file its bug-shaped debts, sweep its
   lexicon with `fdf lexicon`, and map one module with `fdf adopt`.

## Decisions

Decided 2026-09-23:

1. **Bugs.** A new `Bug` type in `bugs/`. Rejected: `Debt` with a `kind:`
   field, and Debt with optional bug sections.
2. **F12 enforcement.** Every document is scanned, as warnings by default.
   `except:` phrases cover other senses, and `DOMAIN.md` may set `strict: true`
   (the same as `--strict-domain`). Rejected: errors by default; a
   Gherkin-only validator with prose reported only by `fdf lexicon`.
3. **Adoption.** An `adopted` status that allows zero-scenario map entries.
   Rejected: requiring ≥ 1 scenario; `done` plus an `adopted:` field.
4. **Names.** As proposed: `bugs/`, `fdf bug`, `fdf mv`, `fdf lexicon`,
   `fdf adopt`, `except:`, `adopted`, and the fdf-adopt skill.
5. **Bugs are never resolved in place.** A repair goes through a Fix or a
   Change (or a task in an in-flight feature). A defect in code no feature
   documents is adopted first, as a map entry, and then repaired by a Change
   that adds the missing scenario. Resolving a bug without a repair is only for
   not-a-defect, a duplicate, or code that is gone. Rejected: resolving in
   place for undocumented code.
6. **`resolves:` edge.** A Fix or Change names the bugs it repairs (written by
   `fdf fix --from bugs/<id>`). F10: each ID names a bug under `bugs/`, or
   once the document is done, one cleared into `bugs/LOG.md`. Once the
   document is done, every bug it resolves that is still in the register is
   `resolved`. F14: a resolved bug that still carries `# Violates` is named by
   a done Fix or Change. Rejected: prose-only linkage.

## Out of scope

- Splitting or merging features. These are semantic, so they are a Change or
  a brainstorm.
- Renaming identifiers in code. That is checkpoint work plus a debt.
- General scenario renames on delivered features. Those are a Change
  (`remove:` plus `add:`); only the lexicon fix renames them in place.
- Scanning `CLAUDE.md`/`AGENTS.md`. The managed primer quotes FDF's own example
  words; fdf-checkpoint covers those files.
- `fdf where <path>`: a reverse lookup of the features, practices, debts and
  bugs that claim a path. It is a natural follow-up once features carry
  `resource`.

Made while the PR was in review, after two audits of `spec/0.7.md`: one for
contradictions and mismatches with the validator, one for readability.

7. **Surface documents and logs get triggers, not just "optional".** A
   feature SHOULD have `slug.surface.md` when it adds or changes something a
   person or another system uses directly. An entry goes in the log of the
   one document it is about, and the root `LOG.md` holds only what concerns
   the bundle as a whole. `fdf log [<id>] "<entry>"` writes to the right log
   and creates it on first use. Evidence: in the dogfood bundle, 4 of 26
   features had a log, while feature milestones went into a 2,800-line root
   log.
8. **A draft may have a log**, and nothing else. Logging then needs no
   special case, and a Change or Fix in `draft` could already have one.
9. **`retires` is declared from the start.** While the Change is in progress,
   the feature is still `done` or `adopted`; once the Change is done, the
   feature is `retired`. It must be in `affects`, and `# Rationale` must not
   be empty. Before this, `retires:` could only be added in the final edit.
10. **Contradictions resolved in the validator:**
    - a shipped release may list a feature retired after it shipped (F7);
    - a retired map entry may have no scenarios (F5);
    - a `remove:` name that a later Change adds back does not break the frozen
      Change that removed it (F10);
    - an open bug's `# Violates` names only delivered features (F14), because
      a feature still being built is repaired by its tasks, which cannot
      `resolves` a bug;
    - `accepted → resolved` is a legal transition for debts and bugs.
11. **Gaps closed in the validator.** These rules were stated but never
    checked:
    - `replaced-by` names a feature that exists;
    - a Change's declaration lines take one of the three forms;
    - plan links reach their own task directory;
    - no `INDEX.md` or `LOG.md` sits inside a grouped Change's task directory;
    - an `except:` phrase contains a real word besides its banned one;
    - the promised soft check on stale `slug.test.md` timestamps now runs.
12. **A cleared bug is always logged.** `fdf bug --cleanup --no-log` is
    refused, because F10 checks a done Fix's `resolves` against
    `bugs/LOG.md`.
13. **The spec text:**
    - a glossary and a "How to read this specification" section (RFC 2119
      keywords, rule codes, process rules);
    - lettered sub-rules in *Conformance*, and a table of which version adds
      what;
    - one term per concept ("cleared", not "retired from the register");
    - examples that pass the validator with no warnings.
14. **F10's exceptions follow time.** A removed name excuses only documents
    earlier than the removal, and an added-back name excuses only the
    earlier removal. The order comes from `timestamp`, and an order that
    cannot be told excuses nothing. Without the order, a new Change could
    hide an add or a removal that never happened behind an old record.
15. **False failures fixed for every pin.** Validators now skip hidden
    directories such as `.git` and `.obsidian`. A bundle at the top of its
    own repository skips R1 with a warning. A `##` line in a fenced block of
    a log is not a heading, and a stub marker quoted in code does not make a
    filled Context document a stub.
